# Agent 评测面试题 · 自问自答（6 题）

> 用法：每题 = 面试官的问题 → 高分作答示范（可以直接说出口的版本）→ 解析（考什么 / 加分点 / 翻车点）。答题语态遵循"面试要结构外显"：第一句给地图，然后展开，有数字、有取舍、结尾闭环。这 6 题覆盖 agent 评测面试的六个高频角度：体系设计、口径判断、离线在线背离、LLM 判官、统计决策、从 0 落地。

---

## Q1 你负责一个订机票的 Agent，怎么设计它的评测体系？

**作答示范：**

"我会分四层搭，先说这个场景的评测核心：**查终态，不是看回复**。

第一层，结果：任务是否真的完成——判定标准不是 Agent 说'已为您订好'，而是查订单库里有没有这条预订、乘客航班价格字段对不对。凡是能程序化校验的，绝不用模型打分。

第二层，过程：轨迹质量——步数效率、工具调用对不对（选对接口、参数合法、正确使用返回值，三个子项分开统计）、出错后能不能自己恢复。订票场景还有一个特有维度：改签退票规则这类**政策遵循**要单独评——能力强但不守规矩，在交易场景等于零分。

第三层，效率：端到端耗时、单任务成本（含重试和多步）。

第四层，安全：是否越权操作、有没有错订误扣款——这层是上线否决项，不参与加权平均。

口径上我会用'多次运行全部成功'代替'至少成功一次'：跑 8 次全成才算稳定，订票用户不会给你重试八次的机会。数据集从真实客服 query 脱敏采样打底，高风险场景（改签、多人、婴儿票）超采；先做 50 条冒烟集把飞轮转起来，线上坏 case 持续回流进集。"

**解析**：考体系化能力，这是 agent 评测的开场必考题。完整结构 = 四层指标 + 判定方式 + 可靠性口径 + 数据集来源，四件套齐了才算答完。加分点："查世界不查嘴"、pass^k 意识、安全层是否决项不是权衡项。翻车点：只罗列指标名不讲怎么判定；张口就是"用 GPT 打个分"；忘了说数据集从哪来。

## Q2 Agent 评测成功率 85%，老板问能不能上线，你怎么答？

**作答示范：**

"我会先确认三个口径再回答——85% 这个数在不同口径下，可以差出一个产品的生死。

一，成功怎么判定的？是 Agent 自己报告'完成了'，还是校验了环境终态？自报口径必然虚高，模型说做完了和真做完了是两回事。

二，是单次成功率，还是多次运行都成？单次 85% 的 agent，连跑八次全部成功的比例可能掉到一半以下——demo 惊艳、日用拉胯的差距就在这。

三，这 85% 是在什么分布上测出来的？评测集如果偏简单高频场景，长尾一上线就露馅。

如果口径都干净，我的上线判断不看单一数字，看三道门：主指标不低于基线；安全类指标零容忍——一次误扣款的损失能吃掉一万次成功的收益，失败成本是不对称的；成本延迟在预算内。三道门都过，先灰度 5-10%，盯在线的人工接管率和投诉率，不直接全量。"

**解析**：考数据素养在 agent 语境的迁移——听到数字先过口径关。加分点：自报完成率虚高、pass^k、失败成本不对称、灰度而非全量。翻车点：直接答"85% 挺高了可以上"；或只会说"要看情况"却给不出具体要看哪三个口径。

## Q3 评测分数很高，但线上用户说"不好用"，怎么排查？

**作答示范：**

"这是典型的离线在线背离，我按三层排。

先怀疑评测集：它的分布是不是过时了。评测集是半年前建的、用户已经在问新问题，离线分就成了'对着旧考卷考满分'。动作：拉最近两周的线上 query 抽样，和评测集比分布，错位就回流重建。

再查中间层的桥：'分数高'测的往往是单步能力——意图识别准不准、检索有没有效；'不好用'可能出在链路层——端到端太慢、中途反复要用户澄清、多轮丢上下文。这些不在离线集里，但用户全感受得到。动作：把'不好用'的投诉按执行轨迹归因分类，看集中在哪一层。

最后补观测：如果日志只记了输入和输出、没有中间轨迹，那先把 Trace 补齐再谈优化——看不见的问题修不了。

最终输出是一份归因分布：多少来自评测集过时、多少来自体验层缺口、多少是真实能力问题，各自配动作。而不是一句'我们去优化模型'。"

**解析**：考归因意识 + 观测意识的组合。结构 = 评测集分布 → 桥梁指标层 → 观测基建，一层层排。加分点："对着旧考卷考满分"这类比喻、把投诉当免费标注回流。翻车点：直接跳到"优化模型/改 prompt"；没有意识到评测集本身会过期。

## Q4 用 LLM 给 Agent 的输出打分，可信吗？

**作答示范：**

"可信度不是有或无，是要挣来的。我的做法分四步。

第一步，判官过资格考：拿两三百条人工标注的金标集测它，与人的一致率要达到人和人之间的水平——通常 85% 上下。达不到不许上岗。

第二步，处理三个已知偏差：偏爱长回答（rubric 里明写忽略长度）、位置偏差（对比式打分交换顺序跑两遍取交集）、自我偏好（判官换另一家的模型）。

第三步，rubric 的写法决定一致率的上限：不问'这个回复好不好，0 到 10 打几分'，而是拆成一组是/否的事实判断——比如评回复是否口语化，就问'是否用您称呼对方、是否出现口语词、是否带语气词'。二元化之后人机分歧会大幅收窄，业内有一致率从 62% 提到 92% 的实践。

第四步，顺序纪律：先做到人人一致，再谈人机一致——评测员之间都对不齐标准，机器对齐无从谈起。团队里要有一个人对标准拍板，标准内容再由真实 case 持续修正。"

**解析**：考 LLM-as-judge 方法论的完整度，AI 评测岗位的核心题。结构 = 资格考 → 去偏 → rubric 二元化 → 对齐顺序。翻车点：说"GPT-4 打分还挺准的"（零校准意识）；三个偏差一个都说不出；不知道人人一致先于人机一致。

## Q5 两个版本：A 成功率 78%，B 76%，选哪个上线？

**作答示范：**

"先说结论：这 2 个点大概率不构成选择依据。

第一，显著性：评测集如果是三五百条，2 个百分点基本在噪声区间——先算置信区间，重叠就当同水平处理，别为噪声开庆功会。

第二，方差：agent 同题多跑波动很大。我会看每个版本跑 5 次的稳定性——平均分高但忽高忽低的版本，用户体感反而更差；多次全成率高的那个更值得上。

第三，能力打平之后，决策还有别的轴：B 如果便宜 40%、快一倍，我选 B；A 如果在高风险场景的安全指标更干净，我选 A。

所以我的完整答案是：补显著性检验和多次运行数据；能力区分不开，就按成本、延迟、安全三个维度拍板。用单一数字给版本排名，是评测最常见的误用。"

**解析**：考统计直觉——最容易暴露"会背指标但没有数据 sense"的一道题。加分点：置信区间、方差与稳定性、多维决策观。翻车点：不假思索选 78% 的人，这道题就是为他们出的。

## Q6 让你从 0 给公司搭 Agent 评测能力，MVP 先做什么？

**作答示范：**

"先说我不做什么：不先设计复杂指标体系，不先建全自动平台——新团队最大的坑就是调研半天设计出一套精妙体系，结果跑不起来、对不齐。

MVP 三件事，两周内能上线：

一，观测先行。把 Trace 打全：每次执行的工具调用、中间结果、耗时全记录。这是地基——看不见的问题几乎不可能被稳定解决，没有它后面全是盲猜。

二，50 条冒烟集。从最高频的核心场景手工攒 50 条任务，每条定义清楚预期行为，每次改动必跑，防止改一处崩一片。

三，坏 case 回流机制。线上每个投诉、每次人工接管，自动变成一条评测样本。

这三件事成本极低，但飞轮就转起来了——评测体系是被 Good/Bad Case 喂大的，不是设计出来的，业内有从 20 个指标一年长到近 200 个的先例。等飞轮转稳，再补全链路回放、自动回归、发布门禁这些基建，让评测从'打分动作'长成'基础设施'。"

**解析**：考落地判断与优先级，管理岗和平台岗高频题。结构 = 先立不做什么 → 三件套 + 时间预算 → 演进路径。加分点：观测先行、飞轮先于体系、"打分动作 vs 基础设施"的格局。翻车点：上来就画大而全的平台架构图——面试官会立刻追问"第一周你到底交付什么"。

## 六题背后的一张地图

这 6 题看似分散，考的其实是同一条链：**怎么定义好（Q1）→ 怎么读数字（Q2/Q5）→ 怎么归因（Q3）→ 怎么规模化判分（Q4）→ 怎么落地运营（Q6）**。任何新的 agent 评测问题，基本都落在这五个位置之一——先定位在哪一环，再调对应的方法作答。
