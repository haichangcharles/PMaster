# PRD 与执行（Execution）

执行阶段的 PM 职责：**让正确的东西被正确地做出来并安全地到达用户**。文档、协作、发布三件事。

## 1. PRD 标准结构（可直接套用）

```
# [功能名] PRD
版本 / 作者 / 评审人 / 状态（草稿→评审中→已定稿→已变更）

## 1. 背景与问题（为什么做）
- 问题陈述：谁在什么场景遇到什么问题，造成什么损失
- 证据：数据 + 用户原声（各至少一条）
- 为什么是现在

## 2. 目标与成功指标（做成什么样）
- 目标（用户视角 1 条 + 业务视角 1 条）
- 成功指标：北极星贡献 + 功能级指标（含当前基线和目标值）
- 护栏指标：不允许恶化的指标（如性能、投诉率）
- **Non-goals（明确不做什么）**：至少 3 条——这是 PRD 里最能防扯皮的一节

## 3. 用户与场景
- 目标用户 + 核心使用场景（用户故事格式：作为X，我想要Y，以便Z）
- 场景优先级：P0 主流程 / P1 重要分支 / P2 边缘

## 4. 方案描述
- 方案概述 + 流程图（用户流 + 关键状态机）
- 逐场景的功能描述与交互说明
- **异常与边界**：空状态、加载失败、权限不足、并发冲突、极端数据量、新老版本兼容
- 数据埋点需求（事件、属性、触发时机——上线后想看什么现在就要埋）

## 5. 依赖与影响面
- 上下游系统、其他团队依赖、对现有功能的影响

## 6. 发布计划
- 灰度策略 / 回滚条件 / 运营与客服物料

## 7. 里程碑与开放问题
```

**PRD 质量自检三问：** 工程师不来问我也能开工吗？测试能直接从中导出用例吗？三个月后新人能看懂当时为什么这么决策吗？

**颗粒度原则：** 写清楚"什么"和"为什么"，把"怎么实现"留给工程师，把"长什么样"留给设计——除非该细节影响用户价值。管得过细是对协作方专业性的否定，也会让 PM 成为瓶颈。

## 2. 用户故事与验收标准

用户故事：`作为 [角色]，我想要 [能力]，以便 [价值]`。价值从缺说明这条故事可能是伪需求。

验收标准用 Given-When-Then：
> Given 用户购物车中有失效商品，When 用户点击结算，Then 弹出提示并允许一键移除失效商品后继续。

每条 P0 故事至少 3 条验收标准（正常流 + 异常流 + 边界）。

## 3. 与工程师协作的核心纪律

- **尽早引入，共同设计。** 方案定型前拉工程师看问题（不是看方案），常能得到"换个做法成本降 10 倍"的信息。
- **讲问题和目标，别指定实现。** "这里需要 2 秒内出结果因为用户在收银台排队"好过"这里要加缓存"。
- **变更有代价意识。** 开发中变更需求时明确说明变更原因，并接受工期重估——频繁"小改动"是 PM 信用破产的最快方式。
- **技术债共治。** 主动给技术债留配额（见 prioritization.md），换取工程团队在冲刺时的信任。
- **估期尊重。** 不砍工程师的估期来倒排；deadline 驱动时砍范围（scope），不砍质量和工期。

## 4. 敏捷执行要点（去仪式化的本质）

- 迭代规划的本质：**用容量约束逼出优先级诚实**。容量 = 人天 ×（1 − 会议/运维损耗率，通常 20-30%）。
- 每日站会的本质：暴露阻塞，不是汇报出勤。超过 10 分钟就变味了。
- 迭代评审（demo）的本质：让利益相关者尽早看到真东西，纠偏成本最低的时刻。
- 复盘（retro）的本质：改流程不改人。每次只选 1-2 个改进项并指定 owner，贪多必然全部不落地。
- Scrum/看板选择：交付节奏稳定选 Scrum，需求流入不可控（运营型、客服型团队）选看板。混合（Scrumban）在国内团队最常见且合理。

## 5. 发布与灰度（Launch）

**灰度发布阶梯（国内标准打法）：**
1. 内部员工（dogfood）→ 2. 白名单种子用户 → 3. 1% → 5% → 20% → 50% → 100%
- 每级停留至少一个完整使用周期（日活产品 24-48h）
- 每级预设**继续/暂停/回滚的量化条件**（如：崩溃率 > 基线 +0.1% 即回滚）
- 客户端产品留后门开关（feature flag），服务端问题秒级关闭不用发版

**上线检查清单：**
- [ ] 埋点验证（灰度首日就要能看到数据，上线后才发现没埋是经典事故）
- [ ] 客服/运营物料就位（FAQ、话术、公告）
- [ ] 新手引导与老用户教育方案
- [ ] 回滚预案演练过（不只是"有预案"）
- [ ] 法务/合规过审（涉及隐私、支付、内容的必须）
- [ ] 数据看板建好（不是上线后再搭）

**Post-launch review（上线后 2-4 周，必做）：** 实际 vs 预期指标、意外发现、决策复盘（当时哪些判断对了错了）、下一步（加码/迭代/接受/下线）。没有这一步，团队永远不知道自己的预测有多不准，排序框架也无从校准。

## 6. 项目风险管理速查

风险四象限应对：高概率高影响 → 立即处理或改变方案；高影响低概率 → 预案 + 监控信号；高概率低影响 → 纳入计划缓冲；双低 → 接受。

**PM 最该盯的三类执行风险：** 依赖方延期（每周主动同步，不等对方上报）、需求理解偏差（开发中期做一次"照着代码走查场景"）、范围蔓延（变更走显式流程，哪怕只是 5 分钟的口头确认 + 群里留痕）。
